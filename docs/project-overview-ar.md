# LogShield - شرح المشروع ببساطة

## 1) ما هو مشروع LogShield؟

`LogShield` هو نظام دفاعي تعليمي وعملي في نفس الوقت، فكرته الأساسية أنه يجمع الـ logs الأمنية، يحللها، يكتشف السلوك المشبوه، يحسب درجة خطورة، ويعرض النتائج في Dashboard احترافية تساعد محلل الأمن السيبراني في المتابعة والتحقيق.

بمعنى أبسط:

- النظام يستقبل أحداث أمنية مثل:
  - محاولات تسجيل دخول فاشلة
  - طلبات Web مشبوهة
  - محاولات SQL Injection أو XSS
  - نشاط غريب من IP أو User-Agent
- ثم يقوم بـ:
  - تخزين الحدث
  - تطبيعه إلى شكل موحد
  - تشغيل Detection Rules عليه
  - إنشاء Alert لو النشاط مريب
  - إسناد Risk Score
  - مساعدة المحلل في التحقيق واتخاذ قرار

---

## 2) الهدف من المشروع

المشروع ليس مجرد Dashboard شكلها جميل، بل منصة SOC Tier 1 دفاعية تساعد على:

- مراقبة الأحداث الأمنية
- اكتشاف التهديدات
- تحليل الـ IOCs
- فحص الروابط والملفات بشكل آمن
- إدارة الـ incidents
- تقديم تجربة تعليمية وإرشادية للمستخدم

يعني المشروع يجمع بين:

- `Monitoring`
- `Detection`
- `Investigation`
- `Response Guidance`
- `Security Awareness`

## 4) فكرة عمل النظام من الداخل

المشروع يعمل تقريبًا بهذا التسلسل:

1. يدخل الـ user على النظام ويسجل دخول.
2. الـ backend يتحقق من الحساب والصلاحيات.
3. لو المستخدم Admin وكان 2FA مفعّل، يطلب OTP قبل الدخول الكامل.
4. بعد الدخول يبدأ المستخدم في:
   - متابعة Dashboard
   - مراجعة Alerts
   - فحص Logs
   - البحث في Threat Intelligence
   - إدارة Incidents
   - استخدام SOC Tools
5. عند دخول logs أو أحداث مشبوهة:
   - يتم تخزينها كـ Raw Logs
   - ثم تحويلها إلى Normalized Logs
   - ثم تشغيل قواعد الكشف Detection Rules
   - ثم إنشاء Alerts
   - ثم ربطها بتحقيق Incident لو لزم

## 6) أنواع المستخدمين في النظام

المشروع يعتمد على `RBAC` أو Role-Based Access Control.

### Admin

له أعلى صلاحيات، مثل:

- إدارة المستخدمين
- رؤية الصفحات الإدارية
- إدارة الـ blocks
- إدارة الـ settings
- إدارة أجزاء حساسة في النظام

### Analyst

مستخدم تشغيلي داخل الـ SOC، وصلاحياته عادة تشمل:

- مراجعة logs
- مراجعة alerts
- فتح incidents
- إضافة notes/evidence
- التحقيق والتحليل

### Viewer

صلاحياته قراءة أو تعلم فقط غالبًا:

- مشاهدة الصفحات المسموح بها
- عدم تنفيذ عمليات إدارية أو تعديل حساس

## 7) ما الذي يقدمه المشروع أمنيًا؟

المشروع متأمن بعدة طبقات، وكل طبقة تحمي من نوع معين من المخاطر.

### 7.1 Password Hashing

كلمات المرور لا تُخزن كنص واضح، بل يتم تشفيرها بشكل آمن باستخدام hashing.

هذا يحمي من:

- تسريب كلمات المرور مباشرة لو حصل تسريب قاعدة بيانات

### 7.2 JWT Authentication + Refresh Tokens

النظام يستخدم Access Token و Refresh Token لإدارة الجلسات.

هذا يفيد في:

- حماية الجلسة
- فصل التوكن قصير العمر عن التوكن الأطول
- إمكانية إنهاء الجلسات بشكل أفضل

### 7.3 Admin 2FA

لو المستخدم Admin، يمكن طلب كود OTP على البريد قبل إصدار التوكن النهائي.

هذا يحمي من:

- سرقة الباسورد وحدها
- وصول غير مصرح به للوحة الإدارة

### 7.4 RBAC

كل مستخدم لا يرى أو ينفذ إلا ما تسمح به صلاحياته.

هذا يحمي من:

- وصول Viewer أو Analyst إلى صفحات Admin
- تنفيذ عمليات إدارية بدون صلاحية

### 7.5 Root Admin Protection

يوجد منطق حماية للحساب الإداري الجذري حتى لا يتم:

- تعطيله
- تقليل صلاحياته
- تغييره بسهولة

هذا يحمي من:

- Lockout إداري
- فقدان التحكم الكامل في النظام

### 7.6 IP Blocking

عند حظر IP:

- لا يستطيع تسجيل الدخول
- لا يستطيع التسجيل
- لا يستطيع استخدام الـ API

ويتم إرجاع استجابة واضحة توضح أن الـ IP محظور.

هذا يحمي من:

- محاولات brute force
- محاولات تكرار الهجوم من نفس المصدر
- إساءة الاستخدام من IP معروف بخطورته

### 7.7 Rate Limiting / Brute-force Protection

يوجد منطق لتقليل أو منع المحاولات المتكررة خاصة في تسجيل الدخول.

هذا يحمي من:

- brute-force attacks
- credential stuffing

### 7.8 CORS Configuration

الـ backend لا يسمح لأي origin عشوائي باستخدام الـ API من المتصفح.

هذا يحمي من:

- استخدام الـ API من واجهات غير موثوقة
- بعض سيناريوهات إساءة استخدام المتصفح

### 7.9 Security Headers

يتم إرسال Security Headers مهمة مثل:

- `Content-Security-Policy`
- `X-Frame-Options`
- `X-Content-Type-Options`
- `Referrer-Policy`
- `Permissions-Policy`
- `Strict-Transport-Security` في بيئات الإنتاج

هذا يحمي من:

- clickjacking
- content sniffing
- بعض أشكال XSS
- تقوية النقل الآمن عبر HTTPS

### 7.10 Input Validation

المدخلات يتم التحقق منها في الـ backend باستخدام schemas والتحقق من القيم.

هذا يحمي من:

- مدخلات غير صحيحة
- أخطاء منطقية
- جزء من محاولات الحقن

### 7.11 XSS Safety

الواجهة لا ينبغي أن تنفذ script يكتبه المستخدم، وتم تصميم الأدوات والتحليلات بحيث تعرض المحتوى كنص بدل تنفيذه.

هذا يحمي من:

- Stored XSS
- Reflected XSS
- تنفيذ أكواد JavaScript داخل الواجهة

### 7.12 SQL Injection Resistance

الـ backend مبني باستخدام ORM واستعلامات آمنة بدل بناء SQL خام من المدخلات.

هذا يحمي من:

- SQL Injection في أغلب المسارات الطبيعية

### 7.13 Safe URL Scanner

فحص الروابط لا يسمح بسكيمات خطيرة مثل:

- `javascript:`

كما يتم رفض بعض الروابط الداخلية أو غير الآمنة حسب القواعد.

هذا يحمي من:

- استغلال أداة الفحص نفسها
- إدخال روابط خطيرة للتنفيذ داخل النظام

### 7.14 File Analysis بدون تنفيذ

في أدوات الـ SOC، تحليل الملفات يتم على مستوى:

- قراءة bytes
- استخراج hashes
- قراءة strings
- اكتشاف IOCs

بدون:

- تشغيل الملف
- فتحه كـ executable
- تنفيذه داخل النظام

هذا يحمي من:

- تشغيل ملفات خبيثة
- سقوط الموقع بسبب تنفيذ محتوى غير موثوق

### 7.15 Audit Logging

العمليات الحساسة يتم تسجيلها في Audit Logs مثل:

- تسجيلات الدخول
- الحظر وفك الحظر
- تغييرات الإدارة
- بعض الإجراءات الأمنية

هذا يفيد في:

- التتبع
- التحقيق
- معرفة من فعل ماذا ومتى

## 8) المشروع متأمن من ماذا بالضبط؟

بشكل مختصر، المشروع متأمن ضد طبقة جيدة من المخاطر الشائعة مثل:

- الوصول غير المصرح به
- brute-force على تسجيل الدخول
- بعض أشكال XSS
- بعض أشكال SQL Injection
- إساءة استخدام الـ API من أدوار غير مصرح لها
- وصول Admin بدون 2FA إذا تم تفعيله بشكل صحيح
- استخدام روابط خطيرة داخل أدوات الفحص
- تشغيل ملفات مشبوهة داخل المتصفح
- self-lockout في بعض السيناريوهات الإدارية الحساسة

لكن مهم جدًا نفهم أن:

- لا يوجد نظام "مستحيل اختراقه"
- الأمان يعتمد أيضًا على:
  - ضبط الـ env variables بشكل صحيح
  - تفعيل 2FA فعليًا في الإنتاج
  - حماية مفاتيح API
  - تحديث السيرفر وقاعدة البيانات
  - مراجعة السجلات والتنبيهات باستمرار

## 9) أمثلة عملية على استخدام LogShield

### مثال 1: Brute Force

لو IP حاول تسجيل الدخول عدة مرات بباسورد غلط:

- النظام يسجل الـ logs
- قد يكتشف النمط كـ brute force
- ينشئ alert
- يمكن ربطه بـ incident
- يمكن حظر الـ IP

### مثال 2: رابط مشبوه

لو المحلل وجد URL غريب:

- يرسله إلى URL Scanner
- يرى verdict و score
- يستخرج domain أو IP
- يربطه بـ incident أو IOC

### مثال 3: ملف مشبوه

لو تم رفع ملف إلى أداة التحليل:

- يتم فحصه محليًا
- استخراج hashes وstrings وIOCs
- تصنيفه مبدئيًا
- بدون تشغيل الملف نفسه

### مثال 4: تحقيق Incident

لو ظهر alert عالي الخطورة:

- المحلل يفتح incident
- يربط به alerts
- يضيف evidence و notes
- يتابع timeline
- يوثق النتيجة

- فيه أدوات SOC داخلية مفيدة

- بعض الحمايات تكون موجودة في الكود لكنها تحتاج تفعيل صحيح في بيئة الإنتاج

## 12) ملخص سريع جدًا

`LogShield` هو منصة SOC دفاعية وتعليمية تقوم بـ:

- جمع وتحليل الـ logs
- اكتشاف التهديدات
- إنشاء alerts
- إدارة incidents
- تحليل روابط وملفات وIOCs
- تقديم أدوات SOC داخلية
- تطبيق حماية مثل:
  - JWT
  - RBAC
  - 2FA
  - IP Blocking
  - Security Headers
  - Rate Limiting
  - Audit Logging

بالتالي فهو مشروع قوي كمشروع تخرج أو منصة تدريب عملية في الأمن السيبراني، لأنه لا يعرض البيانات فقط، بل يساعد المستخدم على الفهم والتحقيق واتخاذ قرار.
